# G23：启动校验完成后的安装/更新入口就绪竞态

## 结论

这次“签名成功，但一键安装和检查并安装更新暂时不可点击；等待一段时间后恢复”属于前端就绪状态竞态，不是签名许可证失效，也不是 U 盘内容损坏。

后端在 U 盘程序启动时会先显示本地窗口，再由后台完成完整 Bundle/AuthentiCode 校验。校验期间返回 `status=starting`、`watchdog=not-running`，安装和更新必须保持禁用，这是安全要求。问题在于旧前端只保存启动时的第一次 Guard 快照，并以 1 秒间隔读取后续状态；昂贵的离线载荷校验完成后没有立即重新读取 Guard，所以界面会在一段时间内继续使用旧的不可用状态。

## 影响

- “一键安装”在启动校验完成前保持禁用，这是正确的 fail-closed 行为。
- “检查并安装更新”在 Guard 还未变为 `authorized/running` 时保持禁用，这是正确的安全门禁。
- 旧实现没有在载荷探测完成后立即刷新 Guard，且正常状态轮询只有 1 秒一次，造成用户看到签名正常但入口仍不可点击。
- 如果机器已经安装了当前版本，旧实现还可能因为 `phase` 使用了过期 Guard 快照而暂时不显示“已安装”。

## 修复方案

### 1. 载荷探测完成后刷新一次 Guard

`OfflineHome` 完成 `offlinePayloadProbe()` 后，在进入最终按钮状态判定前再次调用 `usbGuardStatus()`。最终阶段使用这次实时结果，而不是启动时快照。

### 2. 对明确的 `starting` 状态加速轮询

- `status=starting` 时立即开始短周期轮询，间隔 250ms，最多 60 次；
- 超过快速轮询窗口后回到 1 秒周期；
- `status` 变为 `authorized` 后立即停止快速轮询并保持普通监测；
- `missing`、`mismatch`、`unsigned`、查询失败等状态仍然 fail-closed，不提前开放任何受保护操作。

这样不会绕过签名门禁，只是更快观察到后端已经完成的授权结果。

### 3. 明确反馈等待原因

在 `starting` 期间显示“正在完成启动校验，完成后会自动开放安装和更新；请保持 U 盘连接”，避免用户把暂时禁用误判为签名失败。

### 4. About 页同步处理启动竞态

About 页的 Codex 载荷更新入口也把 `starting` 视为可重试的暂态，最多重试 20 次，并将延迟限制在 1 秒以内；不会永久轮询。

## 不变的安全约束

以下条件仍然必须同时满足，才开放安装或更新：

```text
status == authorized
watchdog == running
signed == true
codexAllowed == true（更新还要求 removable 与 bundlePath）
```

查询失败、状态未知、签名不匹配、U 盘移除或看门狗未运行时，界面和后端都继续拒绝操作。

## 回归验收

- 初始 Guard 为 `starting`，随后变为 `authorized/running`：两处入口自动变为可用，无需关闭重开管理器。
- 初始 Guard 为未签名、状态查询失败或 U 盘缺失：入口仍保持禁用。
- 后端状态接口未改变，未放宽 `require_authorized`、Bundle 完整性或签名检查。
- 前端定向测试：`OfflineHome.test.tsx`、`About.test.tsx` 共 31 项通过。

## 防止复发的规则

涉及异步启动校验、完整性扫描、看门狗租约或本地载荷哈希时，不能只在页面初始加载时读取一次状态，也不能用“按钮可见”代替“授权已实时确认”。必须同时覆盖：

1. 初始 `starting` 快照；
2. 校验完成后的实时状态刷新；
3. 授权、失败、超时、拔盘四类状态；
4. 安装入口和更新入口两个消费者；
5. 失败时保持 fail-closed，成功时无需用户重启页面即可恢复。

发布打包还必须区分“跳过 Authenticode 检查”和“正式内部签名模式”：`SignedRequired` 静态包使用 `-InternalSigned`，不能把 `-SkipSignature` 当作正式签名包构建选项。构建脚本现在会直接拒绝这种组合，避免生成后才在验包阶段失败。
