# G21：卸载二阶段与 USB License 运行期元数据

状态：针对测试机 G21 现象的修复设计与回归契约。

## 1. 现场结论

G21 同时暴露了两个容易混淆、但归属不同的问题：

1. 二阶段收尾失败时，报告虽然可能已经写入，但弹窗只给出“未完成”，没有把失败原因和保留路径直接告诉用户。
2. `usb-license.json` 是管理器在开发策略下创建的运行期 USB 身份元数据。它不应成为静态发行包的普通文件，也不应被二阶段清理当成未知文件；但它仍必须在签名后留在真实 U 盘根目录，否则无法绑定唯一物理介质。

## 2. 不采用的方案

不把 `usb-license.json` 迁移到 `%LOCALAPPDATA%`。License 绑定卷序列号、Bundle 锚点和相对路径，迁到本机会把“这块 U 盘”的身份错误变成“这台电脑”的身份，并破坏换电脑验证。

“移出发行包”的准确含义是：

- 构建器生成的静态发行目录不携带 `usb-license.json`；
- 签名工具把它作为运行期文件，仅写入真实 U 盘 Bundle 根目录；
- 它不进入 `SHA256SUMS.txt`，但由 Ed25519、卷指纹、Bundle 锚点和卸载前快照保护。

## 3. 策略互锁

发行清单的 `usbGuard.signing.policy` 必须与管理器编译策略一致：

| 管理器 | Bundle 清单 | 缺少 License 时的行为 |
| --- | --- | --- |
| `SignedRequired` | `SignedRequired` | 受限启动，绝不自动写入 |
| `DevelopmentAutoEnroll` | `DevelopmentAutoEnroll` | 仅开发联调允许自动创建未签名 License |
| 任意策略 | 相反策略或缺失策略 | 启动失败，避免开发管理器污染正式 Bundle |

这条检查在启动预检、管理器启动和能力包边界重复执行。正式包的静态构建输出还会明确拒绝已有的根级 `usb-license.json` 或 `.bak` 残留；只有签名器在真实 U 盘上完成授权后才允许出现根级 License。

发布脚本同时检查管理器 PE 内的编译期策略标记，防止把旧管理器与新 Bundle 清单拼成“能生成但启动必失败”的发行目录。

## 4. 二阶段清理边界

- USB Bundle 根目录的 `usb-license.json` 是唯一的运行期元数据；它必须是普通文件，并在删除介质前按当前活动租约指纹重新校验。
- 根目录的 `usb-license.json.bak` 只作为原子写入失败时的事务残留识别：不会无条件放行，必须与当前租约指纹一致后才能随授权清理删除；主文件缺失、内容无效或指纹不一致时保留介质并报告具体路径。
- 嵌套同名文件、重解析点和临时文件永不豁免；发现它们时列为具体阻断项并保留介质。
- `%TEMP%\\codex-uninstall-helper-*` 的白名单只允许二阶段自身生成的精确文件；即使文件名叫 `usb-license.json`，落在 helper 目录也不自动放行，避免扩大删除范围。
- 不勾选“删除当前 U 盘安装包”时，卸载计划不包含任何 U 盘路径，License 保持不变。

## 5. 用户可见诊断

二阶段失败时，报告和弹窗均展示有限长度的：

- 阶段失败原因；
- 状态为 `failed`、`deferred`、`preserved` 或 `warning` 的项目；
- 每个项目的具体路径和详情；
- 完整报告位置。

详细日志仍只写入 `%LOCALAPPDATA%\\CodexAppManager\\logs`，不再写入桌面。输出受数量和长度上限约束，不把整个日志或密钥内容塞进弹窗。

## 6. 验收条件

1. 全新静态发行目录没有 `usb-license.json`、`.bak` 或签名事务残留。
2. 开发 Bundle 可以在明确的 `DevelopmentAutoEnroll` 策略下自动注册；正式 Bundle 或策略不一致时不会自动注册。
3. 带合法根级 License 的授权介质可以在显式选择删除介质后完成二阶段清理；不带 License、指纹不匹配、`.bak` 残留或未知文件时 fail closed，并列出具体路径。
4. 二阶段 helper 出现未知文件、Token 不匹配、即时删除失败或重启兜底登记失败时，弹窗不再只显示“未完成”。
5. 不勾选删除介质的普通卸载不触碰 U 盘 Bundle。
