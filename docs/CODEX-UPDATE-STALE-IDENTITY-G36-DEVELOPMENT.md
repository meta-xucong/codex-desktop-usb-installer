## 2. 根因与契约

### C1：镜像身份只能绑定稳定发布事实

镜像 `/latest/manifest` 是别名资源，可能因同步时间、ETag 或生成时间变化而重新生成。检查/确认一致性不得把这些动态字段当作发布身份；必须继续绑定架构、应用版本、MSIX package version、package moniker、MSIX 大小、选中 MSIX SHA256、checksums SHA256 和 manifest schema。实际下载、checksums、Authenticode 和 MSIX identity 校验仍保持不变。

因此镜像的内部 `releaseId`/`manifestSha256` 改为稳定字段摘要；checksums 文件只绑定选中的 Windows checksum 记录，不受无关平台资产追加影响。真实版本、包摘要或尺寸变化仍必须触发过期保护。

### C2：确认失败后自动重新检查一次

Codex 更新确认返回 `stale_expectation` 时，前端不得只留下没有上下文的静态提示。它自动执行一次新的只读检查：

- 有新候选：关闭旧确认对象，展示新版本确认框，并说明远端信息已刷新；
- 无更新：显示已是最新；
- 检查失败：显示可展开的具体诊断；
- 只允许这一轮自动重检，不循环自动安装，不绕过后端二次校验。

### C3：保留安全拒绝并改善诊断

源地址、版本、资产摘要、U 盘快照或授权根发生变化时仍拒绝提交。后端给出可区分的稳定原因，前端在详情中保留后端诊断，而不是吞掉为“更新信息已过期”。

### C4：中转同步是外部运维事项

本次客户端修复不伪称已修改 VPS。中转需要单独同步到镜像同一 Release 并通过公网验收；在同步完成前，自动模式以可达且版本更新的来源为准，显式选择中转时仍严格使用中转，不偷偷切源。

## 4. 验收矩阵

- R1：仅改变镜像 `generatedAt`/等动态顶层元数据，检查和确认身份相同；
- R2：改变版本、package moniker、MSIX 大小或选中 SHA，身份不同并拒绝旧确认；
- R3：`stale_expectation` 后最多自动检查一次；新候选会重新要求确认，不能静默安装；
- R4：重检失败或其它错误可展开查看后端诊断；
- R5：现有 Codex source、USB 快照、完整性和事务测试不回归；
- R6：格式检查、Rust 单测、前端类型/测试通过；最终版本固定后再独立审计。

## 5. 交付边界

本地代码和测试通过不等于 VPS 已同步，也不等于真实 U 盘更新已经完成。需要重新打包时，必须在上述客户端改动完成并通过审计后重新生成安装器；Skill Hub 成功与 Codex payload 更新是两个独立验收项。
