# 模型档位完整探测与直接添加（2026-10-24）

## 目标

修正模型添加流程，把减少重复校验与减少能力探测分开处理：完整探测当前线路接受的思考档位；用户对候选模型点一次添加后，探测成功即自动写入，无需第二次点击或探测后的 Codex CLI 兼容性门禁。

“探测成功”定义为当前线路对该模型至少有一个显式 reasoning effort 请求返回有效成功响应。成功集合只包含被当前线路接受的档位。某档明确不支持时继续检测其余候选；网络或其他不确定失败时停止后续请求，但若此前已有至少一个档位成功，仍以该成功子集直接添加。未成功、未确认的档位不写入。

## D/I/A 与边界

- **D1**：目标明确，限于上游模型发现、思考档位探测、直接添加及其回归测试。
- **I2**：涉及 UI、一次性探测凭证、Rust 模型目录写入、现有 Codex 模型和配置/MCP 保留。
- **A2**：reasoning 探测会发送上游生成请求，可能计费；真实上游探测只在用户从 UI 点击添加时发生，本地测试使用 mock，不发付费请求。
- 不改 CCSwitch、API Key、MCP 注册/启动、签名、安装器发布、卸载、Reset 语义。
- 工作区含大量既有未提交改动；只修改本文和实现清单内的文件，不回滚或整理其他改动。

## 目标流程

1. 用户点一次“探测并添加”。单模型思考档位探测直接发送候选 generation 请求，不为这次点击重复请求 `/models`；发现页和批量能力探测仍使用目录请求。
2. 在发起 generation probe 之前，检查目标 CODEX_HOME、管理器目录权属和配置是否可安全写入。首次启用管理器目录所需的 Codex 原生默认目录也在 generation probe 前准备好；准备失败时不消耗上游 reasoning 请求。
3. 对精确模型 ID 逐个探测 Codex effort 候选集 `none, minimal, low, medium, high, xhigh, max`；已知不适用的值（如 Claude Opus 5.5 的 `none`）继续排除。每个候选最多发一条请求，不因网络结果重试同一候选。明确不支持的档位继续检测；已有一个档位成功后，如后续候选遇到不确定错误，则停止并添加已验证子集。
4. 若没有任何候选成功，报告“当前线路没有可用思考档位”，不写入模型。至少一个候选成功即构造目录条目并自动提交。默认值优先 `medium`，否则优先 `low`，再否则采用 Codex 顺序中的首个已接受值。
5. 同一 `slug` 只有在配置仍引用该管理器目录时才返回 `already_added`。若管理器拥有的目录文件存在但配置引用已断开，点击操作只恢复管理器目录引用并保留已有条目；不把脱链文件误报为当前已启用模型。
6. 页面显示最终通过/失败和已接受档位。按钮文案/辅助说明在一次点击前提示最多探测请求数及可能产生费用，不额外增加确认步骤。

## 删除的阻断门

- 探测成功后等待用户再次点“确认添加”。
- 单模型强度探测不再重复请求 `/models`；精确模型 ID 的有效 generation 响应本身证明上游可用。Add 不再重新请求 `/models` 或比对上游目录摘要。一次性凭证仍保留必要的安全边界：精确模型/请求、provider/base、签名账号绑定摘要、API Key 摘要、reset epoch、有效期及单次消费；去掉的是提交阶段重复探测和“剩余时长必须覆盖十分钟验证预算”的门槛。
- 写入候选目录前后启动随包 Codex CLI `debug models` 做完整语义回验。用本地必需字段/JSON 结构检查和实际持久化结果替代该不稳定外部进程门。
- 因全局 `model_reasoning_effort` 不在新模型接受集合中而拒绝导入。添加模型不修改用户全局设置。
- 同 slug 时更新原条目的推理元数据。重复模型直接返回已有状态。
- Add 完成后重新读取整个 catalog 作为成功条件。成功由原子写事务结果和本次产生的 model IDs 返回；写入异常按实际失败/恢复状态报告。

## 必须保留的写入保护

- 不允许覆盖非管理器拥有的 `model_catalog_json` 或非管理器目录；损坏的配置/目录不得被猜测修复。
- JSON/条目基础结构、唯一 slug、默认 effort 属于已接受集合的检查。
- 模型目录与 config.toml 只做局部托管块更新；配置其他原文（尤其 `[mcp_servers.media_generation]`）保持不变。
- 保留模型目录互斥锁、快照冲突保护、原子替换、已知良好备份和失败恢复。外部并发改写、磁盘/权限故障等实际 I/O 条件可能阻止提交，并必须准确报告；不得宣称此类故障下也能保证写入。
- 首次原生模型目录准备会在调用随包 Codex CLI 时释放共享配置锁；CLI 返回后重新检查配置/目录快照，避免长时间阻塞其他 Codex 配置操作。
- 如果提交阶段返回可重试的本地前置失败，前端最多使用同一探测凭证自动重试两次，不重复发送上游生成请求。
- 已有相同 slug 若当前已启用，返回幂等结果 `already_added` 并保持旧条目原样；脱链目录则只重接配置引用，不改模型条目。
- 三次自动 Add 前置重试耗尽后保留未过期的一次性凭证，按钮切换为“重试添加”；再次点击只重试本地 Add，不重复发送 generation 请求。凭证过期、配置复位或重置时清除该重试状态。
- Add 失败不能用空模型 ID 列表覆盖 UI 中已有的启用状态；提交结果不确定时读取本地目录状态核实。

## 验收

1. UI 一次点击发起强度探测；无需第二次添加点击。
2. 后端接受并检测全部适用候选值；一个候选成功不会提前结束；每个候选最多一个 generation 请求。
3. 明确不支持继续检测；至少一个已接受值时后续未知错误不阻止添加，未知值不写入。
4. 默认值属于已接受值；完整成功列表均写入 `supported_reasoning_levels`。
5. 探测成功后不调用 Codex CLI `debug models`；全局强度冲突不会拒绝导入或更改用户设置。
6. 首次目录初始化准备失败发生在 generation 请求之前；探测成功后常规模型写入不再依赖 native default / final CLI probe。
7. 相同 slug 的活动目录保持旧条目原样；脱链目录重新接入后保留旧条目。新增/重接时保留原模型、MCP/TOML 段和其他配置。
8. 前端定向测试、Rust 定向测试与项目静态检查通过；不可运行的检查如实列明。
9. 独立只读代码审计 PASS；若审计或验证发现问题，修复后对最终版本重新审计。
