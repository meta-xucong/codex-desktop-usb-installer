# 首次添加模型保留 Codex 原生模型

日期：2026-10-14
范围：模型管理“添加到 Codex”首次写入时保留 Codex 当前随包原生模型。

## 现象与根因

已有目录中的后续添加会读取当前受管目录并追加新项；只有首次添加（`codex-usb-native-model-catalog.json` 尚不存在）会从空 `models` 数组开始，写入 `model_catalog_json` 覆盖配置。Codex 将该文件视为完整模型目录，因此原生模型不再显示。既有回归测试只验证“已有受管目录时追加”，没有覆盖首次添加。

## 行为约束

1. 首次添加时，以及“恢复默认”留下的空白脱离目录后再次添加时，从当前随包 Codex 可执行文件的隔离 `debug models` 输出读取原生模型目录，再把用户已测试的上游模型追加进去。
2. 后续添加只追加到当前受管目录，不删除原生模型或先前添加的模型。
3. 用户选择“恢复 Codex 默认模型”时，清空管理器添加的上游条目并移除管理器配置引用，Codex 回到原生模型目录；脱离引用的目录文件会保留。启动安全检查可因目录未经验证而停用引用，但不能借此清空模型条目；这类生命周期路径不属于用户的“重置模型列表”操作。
4. 原生目录读取、解析或 Codex 校验失败时中止写入，不回退为空目录。
5. Codex 子进程使用现有的隔离临时环境、清理后继、限时和有界 stdout/stderr 捕获；不读取用户 `CODEX_HOME` 配置或密钥。

## 修改边界

- `src-tauri/src/app/model_native_probe.rs`：复用现有 `TemporaryArea`、`configure_command` 和 `win_process::capture`，增加读取当前 Codex 原生模型目录的有界函数。
- `src-tauri/src/app/model_catalog.rs`：首次添加使用该目录作为种子；后续仍读取已有受管文件；受管配置引用存在但目录缺失时拒绝自动重建。
- 上述模块单元测试：覆盖首次添加保留原生模型、第二次添加保留先前模型、恢复默认不再启用覆盖、原生目录读取失败不写入。

不改 UI、上游探测、连接凭证、Codex 启动方式、签名器、VPS、安装器配置格式或非模型管理功能。打包不属于代码修复本身，须在实现、测试和独立审计通过后再决定。

## 验收

- 合成原生目录 `{gpt-native-a, gpt-native-b}` 首次添加上游模型 `vendor/a` 后，三者全部存在且顺序稳定。
- 第二次添加 `vendor/b` 后前四者均保留；重复添加不产生重复项。
- 不存在的目录在 manager config 已引用时不得静默重建。
- 失败时 config/catalog 文件无部分写入。
- Windows bundled Codex 实测 `debug models` 可在隔离 `CODEX_HOME` 得到默认模型，并能校验含原生与上游模型的目录。
- 前端和 Rust 回归测试通过；独立只读审计通过。
