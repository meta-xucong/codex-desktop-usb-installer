# v0.5.17 卸载二阶段与机器残留闭环审计

日期：2026-09-06。输入现场：Windows 10 22H2 上 v0.5.15 联合卸载显示“二阶段清理未完成；exit code: 0”，`%TEMP%\codex-uninstall-helper-<GUID>` 保留约 20 MB；另有当前用户包已不存在、但 AppX 机器投影仍返回精确 Codex FullName 且 `InstallLocation` 为空的残留。v0.5.16 的安装前孤儿修复保留，本版补齐纯卸载路径与最终助手协议。

## 结论与报告纠偏

现场报告提供了有效证据，但以下推论不作为实现依据：

- `parentPid` 在助手清理时已经退出是正常交接条件，不是失败；助手在启动时已验证并持有父进程句柄，真正失败的是第三层 PowerShell 收尾进程未写入 ready 就退出。
- `policy_changed=true` 对应本产品记录的 `RestrictAppDataToSystemVolume` 数据策略事务，不能推断写入了 `AllowDeploymentInExternalVolumes`。现行实现不把后者作为本产品写入项。
- 不直接删除 `PackageRepository`、协议扩展或受 TrustedInstaller 管理的 WindowsApps 入口。它们是 Windows 部署服务的私有一致性状态；本版只使用 `Remove-AppxPackage -AllUsers` 和 WinRT `PackageManager.RemovePackageAsync(..., RemoveForAllUsers)`。

## 根因

1. 旧收尾器通过 `.NET Process.StartTime.ToFileTimeUtc()` 与 Win32 创建时间比较父进程身份。在部分 Windows 版本／令牌边界上，精度或查询行为不一致会使收尾脚本在建立 ready 握手前退出。
2. 旧脚本捕获异常后仍以 0 退出，且未向助手传回失败原文；上层只能生成自相矛盾的“未完成 / exit code 0”。
3. 助手用无限期原生消息框显示结果。用户不点击时，20 MB 助手 EXE 始终被自身进程映射，目录自然无法自删。
4. 联合卸载的终态只严格检查当前用户注册。若失败部署留下无用户的机器级 Staged 对象，卸载可以进入最终清理并删除恢复证据，下一次安装再被旧状态阻断。

## 实现

### 二阶段最终助手

- 助手创建 `lifetime.lock`，以 create-new、拒绝共享的文件句柄绑定随机 nonce。收尾器先原子写入 `finalizer.ready`，再等待该锁真正释放；不再依赖 PID 或启动时间换算。
- 收尾器失败时将具体异常原子写入 `finalizer.error.txt`，并以 2 退出；0 但没有 ready 也被视为协议错误。错误文件最多 16 KiB。
- 助手发现收尾器过早退出或 10 秒内无 ready 时，只终止自己创建且句柄身份一致的子进程，保留准确错误并把最终报告标记为 partial/failed。
- 结果窗口在独立线程显示，最多等待 60 秒；超时后助手可退出，不再因无人点击永久占用自身 EXE。
- 收尾失败后，使用 `MoveFileExW(MOVEFILE_DELAY_UNTIL_REBOOT)` 兜底登记精确 UUID 助手目录中的已知普通文件。目录含未知文件、重解析点或身份不匹配时拒绝登记；不使用通配符或递归删除。
- 启动时可清除只含已知文件且已无活动进程的旧助手目录，也会移除所有已知文件已消失后遗留的空 UUID 目录。
- 删除管理器日志树前，把最新日志最后 64 KiB 嵌入用户可见卸载 JSON；诊断证据不再随 WebView/日志缓存一起消失。
- 对 `wangnov`、`CodexAppxDataBackups` 等父容器只做“确认为空再删除”，不递归触碰其他产品或未知数据。

### 机器级 AppX 残留

- 当前用户卸载成功后，再查询 `Get-AppxPackage` 当前用户、`-AllUsers`、在线预配记录、`PackageUserInformation.InstallState` 与精确包路径状态。查询失败不是“没有残留”。
- 只有一个满足以下全部条件的对象进入候选：官方 PFN；x64 精确 FullName 形状；无当前用户注册；无预配记录；所有已列出的 Owner 均为 `Staged`；`InstallLocation` 为空，或路径不存在，或是目标已丢失的精确系统 Junction。
- 删除授权不是候选记录自己提供的。管理器从当前 USB bundle 重新校验 manifest、文件大小、OpenAI Marketplace Authenticode、包身份／版本／架构，得到唯一允许删除的 FullName；它必须与候选逐字不区分大小写匹配。
- 默认保留数据时，先从当前用户精确包数据目录读取真实内容。Windows 创建的 WpSystem Junction 只有在 SID、包身份、卷 GUID、标准子路径、无多跳／循环均通过时才被展开备份；文件逐一 SHA-256，删除前再次复核。备份失败则不调用任何删除 API。
- 删除前再次查询所有权；先调用 `Remove-AppxPackage -Package <exact> -AllUsers`，重查仍为同一孤儿才调用 WinRT 回退。任何时刻出现 Installed/未知 Owner、预配记录、版本变化或有效路径都停止。
- API 返回后最多等待 10 秒核验精确 WindowsApps 系统入口消失。仍存在或不可读取时报告部分失败并保留恢复记录；不以“机器查询为空”代替文件入口终态。
- 有 AppX 卷恢复日志但 PowerShell 已显示包不存在时，用签名授权的精确 FullName 做一次 WinRT reconciliation；“包不存在”只有在重新查询与系统入口审计均干净时才可作为成功。
- 机器状态未闭环时不启动最终助手、不清除 AppX 卷／策略事务记录，用户可原地重试。

## 无法由本产品绕过的边界

- AppX 服务损坏、企业 AppLocker/WDAC、UAC 被拒、另一个用户／预配包仍有效、Windows 正式删除 API 均失败，不能通过私有注册表或夺权强制绕过。
- 如果 Windows 私有数据库存在一个连正式 AppX 查询和两条删除 API 都不可见的坏记录，本产品不会直接手术私库。失败日志和恢复记录会保留，需依据 Windows 部署 ActivityId 继续诊断或修复系统组件。
- 重启删除是占用场景的最终兜底；在重启实际发生前，报告会明确标记 scheduled/pending，而不是声称已经物理删除。
