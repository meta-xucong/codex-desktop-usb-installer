# v0.5.20 — U 盘程序 / 本机数据架构审计

日期：2026-09-06。范围：用户提供的 v0.5.19 目标机实测报告、当前 Windows 安装与
卸载实现、离线发行布局、U 盘绑定以及后续 Skill/MCP 内容边界。

## 结论

v0.5.19 的“程序在 U 盘 AppXVolume、数据请求留系统卷”不能稳定满足产品契约。
目标 Windows 10 机器已经观测到 `%LOCALAPPDATA%\Packages\OpenAI.Codex_*` 的标准
子目录被 Windows 建成 Junction，目标为 `<USB>\WpSystem\<SID>\...`。API 成功、策略
回读、`AppDataVolume` setter 回读或安装结束时数据尚未创建，都不能证明首次运行后数据
仍在本机。

v0.5.20 废止新装 AppXVolume 路线，改为：

- 固定、验签 MSIX 仅作为受信归档；
- 程序事务性解包到当前授权 bundle 的 `apps\Codex`；
- `CODEX_HOME` 显式固定为 `%USERPROFILE%\.codex`；
- 桌面端继续使用 Windows 默认 `%APPDATA%\Codex`、`%LOCALAPPDATA%\Codex`；
- 安装前同时核验声明盘符和真实解析盘符均不等于产品 U 盘；
- 不调用 AppX Stage/Register/Move、新建 AppXVolume 或外部卷策略；
- 旧 AppX 逻辑只用于迁移/卸载兼容，不再参与成功的新装主路径。

这使“程序在 U 盘、可变数据在本机”成为普通文件系统边界，而不是依赖 Windows 打包
应用跨卷数据策略的期望值。

## 根因证据

1. 目标机 `AC` 等目录的 Attributes 为 `Directory, ReparsePoint`，LinkType 为
   `Junction`，目标精确落在 U 盘 `WpSystem`。
2. 该布局由 Windows AppX 部署机制生成，不是安装器手工创建。
3. 首次物化前接受 `not-created`，使安装器能先报成功、应用运行后才暴露错误卷。
4. 跨卷 Junction 又与旧版备份、回滚、错卷清理及孤儿 AppX 状态形成连锁故障。

## 代码变更

### 安装

- `commands.rs`：USB 模式只接受由当前进程位置和有效 U 盘租约推导出的
  `<bundle>\apps\Codex`，不接受前端或持久化配置中的旧 C 盘路径。
- `win_update.rs`：新增 `portable-usb` 安装模式，USB 计划始终进入安全解包路线；
  `msix-usb-volume` 仅保留为历史状态标记。
- `portable.rs`：新增 USB 专用副作用策略。安装前不启动 Codex，不创建直接开始菜单和
  卸载入口；解包拒绝绝对路径、父目录跳转、链接类条目及写入长度不一致。
- 便携树使用同卷 staging/rollback/rename 事务；崩溃恢复记录仍覆盖每个不可逆边界。
- 安装完成后以精确便携入口和 manifest 作为成功条件，并记录 USB 程序路径与三类本机
  数据路径。

### 数据位置

- `usb_guard.rs` 增加本机数据路径模型。
- 对 `%USERPROFILE%\.codex`、`%APPDATA%`、`%LOCALAPPDATA%` 先检查声明盘符，再
  canonicalize 最近存在父目录；Windows 返回的 `\\?\C:\...` 统一解析为 `C:\`。
- 任何声明或解析后位置等于授权 U 盘都会在写程序前失败。
- Codex 启动和主题/CDP 启动均显式传入本机 `CODEX_HOME`。

### 启动与防绕过

- USB 安装不发布直达 `Codex.exe` 的开始菜单项或卸载元数据。
- 唯一支持入口仍为 `CodexDesktopSetup.exe`；管理器只启动授权 U 盘精确程序根。
- 现有卷序列号、锚点哈希、bundle 相对路径租约和拔盘五秒终止保持不变。

### 卸载与介质清理

- 普通卸载识别当前 bundle 的 `apps\Codex`，关闭对应进程后清理该精确程序树；本机
  用户数据默认保留。
- 介质删除的前置只读核验可以临时接受唯一的 `apps\Codex` 受管运行目录，但不枚举或
  把它纳入发行哈希。
- 主卸载结束后，清理助手重新以严格模式打开发行包；若 `apps\Codex` 仍存在则拒绝
  删除介质。未知文件、未知 Skill/MCP 和重解析点同样保留并报告。
- `apps`、`content` 及三个说明文件纳入发行允许清单；删除顺序仍为子目录到父目录。
- 旧版精确 AppX 遗留可通过受支持 Windows API 清理；仍禁止编辑
  PackageRepository/StateRepository、夺取 WindowsApps 权限或递归删除系统目录。

## Skill / MCP 设计边界

发行包新增：

```text
content/skills/README.txt
content/mcp/README.txt
```

当前状态为 `layout-ready-import-later`，不是“已自动导入”。Codex 支持从本地发现目录
加载 Skill，也支持指向 Skill 文件夹的符号链接；后续导入器可让载荷留在 U 盘。Codex
的 MCP 配置位于 `~/.codex/config.toml` 并由桌面端、CLI 和 IDE 共用，因此 MCP 二进制
可留在 U 盘，但配置、密钥及盘符映射必须在本机管理。

- Skill 文档：<https://developers.openai.com/codex/skills>
- MCP 文档：<https://developers.openai.com/codex/mcp>

## 发布清单契约

`usb-manifest.json` 不再包含 `appxVolume`，改为：

- `programLayout.mode = verified-msix-extraction`
- `programLayout.codexRoot = apps/Codex`
- `usesAppxVolume/createsWindowsApps/createsWpSystem = false`
- `dataLayout.onUsb = false`
- `dataLayout.observedBeforeInstall = true`
- `managedContent.skillsDirectory = content/skills`
- `managedContent.mcpDirectory = content/mcp`
- `managedContent.configLocation = %USERPROFILE%/.codex/config.toml`
- `managedContent.secretsIncluded = false`
- `managedContent.status = layout-ready-import-later`

验证脚本对上述字段、目录、说明文件和 `WindowsApps/WpSystem` 不存在性作强制断言。

## 仍需目标机验证的边界

自动测试可以证明路由、路径、归档安全、事务和发行清单，但不能替代真实 Codex 桌面
进程运行。因此 v0.5.20 的目标机验收必须确认：

1. 新装前 U 盘无 `WindowsApps/WpSystem`，新装和首次启动后仍无；
2. 程序位于 `<bundle>\apps\Codex`；
3. 首次启动后数据仅在 Windows 正常用户目录产生；
4. Codex 能读取本机既有历史状态并正常保存新会话；
5. 直接从管理器启动、拔盘五秒结束、重插恢复均正常；
6. 普通卸载删除 USB 程序但保留本机数据；高级清理仅在再次确认后删除所列数据；
7. 旧 v0.5.x AppX 残留若存在，兼容清理报告与 Windows 实际终态一致。

开发机不会为测试真实调用 AppX 部署/移除、写 HKLM 或修改 WindowsApps。目标机失败时
应保留管理器完整日志，不能通过手工删注册表、夺权或删除恢复 journal 来制造成功。
