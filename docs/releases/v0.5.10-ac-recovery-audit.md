## 原生恢复路线的依据与调整

微软 `RegisterPackagesByFullNameAsync`（Windows 10 19041）支持 `RegisterPackageOptions.AppDataVolume`，可按精确 FullName 指定用户数据卷。程序先 Stage 到 USB，核验实际 staging 位置，再 Register 并指定唯一系统数据卷，不借助全局默认卷，也不主动把程序部署到 C。

仅重注册不是既有数据迁移保证：本机只读微软 AppXDeployment-Server 事件元数据 756 明确存在“数据已在另一媒体卷”拒绝分支。故本次实现受控恢复事务：严格备份 → 持久记录 → Windows 正常移除精确当前用户注册 → Stage USB → Register 系统数据卷 → 恢复备份 → 双重实际位置与内容核验。

恢复作者新增范围：`crates/codex-win-engine/src/appx_data_recovery.ps1` 与 `tools/test-appx-data-recovery.ps1`，原只读研究 Agent 转任开发；独立审查者不变。sys.rs 作者负责脚本注入和主流程接线，并获准仅增加 lib.rs 导出。主控补充 appx_volume.rs 的原生只读卷 GUID 捕获、卸载授权上下文与版本文件。

IR-05：注册结束到第一次库存之间可能有新用户内容，不能把“等于库存”认定为 Windows 默认文件。修正设计：恢复原始数据前，另做新注册后数据的完整校验备份并记录到 journal；只有当前数据仍与该快照相符时才恢复覆盖。新旧两份均保留，提示不声称自动合并。备份失败或随后变化必须停止覆盖。

IR-06（独立复现，修复中）：新恢复脚本最初的目录 pin 仅申请 READ_ATTRIBUTES 并共享读写。审查在唯一隔离空目录实测，第二个写句柄仍能 FSCTL_SET_REPARSE_POINT 将目录原地转为 Junction；仅改 share 为 READ 仍不充分。必须通过实际对抗测试证明阻止原地重定向，不能仅检查初始属性或防止 rename。现有卸载目录 pin 的同源风险也纳入必要修复，其他清理范围不变。

IR-06 修正：仅 FILE_WRITE_ATTRIBUTES 的变更句柄仍能绕过 READ-only sharing，撤销单改 share flags 的无效修复及不充分测试。恢复／备份作者改为 NtCreateFile 的 RootDirectory 逐组件访问与 OBJ_DONT_REPARSE；主控新增 `src-tauri/src/app/uninstall_tree.rs`，同样以相对句柄打开、原生句柄枚举和 SetFileInformationByHandle 删除，不改 ACL、不改清理目标白名单。实际隔离测试在“读完目录属性之后、打开子项之前”成功注入 FSCTL 原地 junction；子项打开被拒，外部 `keep.txt` 保持原字节，卸载 19/19 通过。此为中间版本证据，最终冻结仍需独立复核。

IR-07：恢复暂存文件原在备份目录创建后同卷 rename 到数据目录，可能保留备份 ACL，而非 Windows 创建的包数据目录权限。按[微软同卷移动权限说明](https://learn.microsoft.com/en-us/troubleshoot/windows-client/windows-security/permissions-on-copying-moving-files)纠正：在已核验目标父目录中相对创建 journal 绑定的随机暂存文件，自然继承该目录权限，再以相对句柄改名；旧内容仍留独立备份。运行时不调用 SetACL，不复制旧 WpSystem 的跨卷 ACL，不以“内容哈希一致”替代实际可访问性设计。

IR-08：独立审查发现升级分支可能先 Move 既有 C 盘包，再由恢复模块拒绝更高版本／未知位置。已交 Engine 作者仅补充 Move 前的位置、版本及已停止进程门禁和“0 Move”反例，不能把拒绝后的停止当作没有发生迁移。

IR-09：独立审查发现保留数据卸载的重试循环原来仅在首次调用前复核备份。若首轮忙／失败后出现新数据，后续重试可能删除未备份的新内容。仅补每次 Remove 前再次复核原备份／数据不存在条件和对应中断反例，不扩大清理范围。
