# v0.5.15 — WindowsApps Junction 核验与修复审计

日期：2026-09-05。范围：用户转发的 WorkBuddy“系统 WindowsApps Junction → USB 悬空链接导致反复失败”线索。旧 v0.5.14 发行目录保持不变。

## 核验结论

| 转发报告的判断 | 本次核验 |
| --- | --- |
| 安装器手动创建了 C 盘 WindowsApps Junction | 当前生产源码未发现该创建操作。`mklink /J`、`New-Item -ItemType Junction` 在隔离测试中使用；生产程序交由 AppX Stage/Register/Move/Remove 管理包目录。不能仅凭目录存在断定创建者。 |
| 缺少 `AllowDeploymentInExternalVolumes=1` 必然禁止 USB Stage | 未找到支持这项必需设置的微软公开依据。本地 AppxPackageManager.admx 与公开文档对应的程序卷限制是 `RestrictAppToSystemVolume`，未配置不代表强制系统盘。没有新增未经证实的注册表值，也没有修改组织策略。 |
| InstallLocation 为 C 盘即证明错装 | 不充分。Junction 可指向另一本地卷；旧版多处只比较盘符，确实存在误判有效别名的代码缺陷。 |
| Windows 没清掉链接就应直接以 TrustedInstaller 权限删除 | 不采纳。当前代码没有“自己手动创建”的系统链接所有权证据，强删可损坏 Windows 部署状态。使用精确包卸载 API，随后只读核验；残留或读取未知时明确未完成并保留恢复记录。 |

微软原始资料：[程序卷限制及注册表映射](https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-applicationmanagement#restrictapptosystemvolume)、[Junction 的跨本地卷语义](https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions)、[按目标卷 StagePackageAsync](https://learn.microsoft.com/en-us/uwp/api/windows.management.deployment.packagemanager.stagepackageasync?view=winrt-28000)、[Remove-AppxPackage](https://learn.microsoft.com/en-us/powershell/module/appx/remove-appxpackage?view=windowsserver2025-ps)。这些资料说明接口／链接语义，不证明目标机的具体链接由哪次部署创建或 Stage 的真实失败原因。

## 已实现的修复

1. **程序落点核验**：新增只读 `appx_package_path.ps1`。只有精确官方 x64 FullName 的系统包目录，且类型为单目标目录 Junction，目标为绑定 USB 的同名包目录，WindowsApps 与包目标均存在且为普通目录，复读链接目标未变时，才接受为别名。远程路径、路径穿越、ADS、错包、多跳、悬空和读取错误不授权成功。原始 InstallLocation 保留用于溯源；`packageVolume` 用已核验的实际卷。
2. **受控恢复**：Stage/query/Register 之间的位置后置条件使用相同解析规则。仍通过绑定的 PackageVolume 查询精确、健康的包，不能只凭链接存在跳过 Stage。原恢复记录的身份、SID、载荷哈希和物理卷门禁均保留。
3. **安装前同路径证据**：每次确需 Stage 时，在原恢复记录中写入 `systemEntryBeforeStage`；它只做诊断，不授权删除链接或覆盖其他内容。可继续 Windows 自身能处理的 Stage；原生失败保留 HRESULT、ActivityId、部署结果和链接状态。旧版恢复记录没有新增字段也可以继续。
4. **启动与运行检查**：健康探测及恢复前进程检查同时识别经核验的别名与实际包根目录。目录边界按完整组件比较，旁边的其他安装不算本包。恢复前检查覆盖当前包两种桌面入口文件名 Codex.exe / ChatGPT.exe，只读判断是否需要用户关闭，不按名字杀同机应用。
5. **精确 staged-only 清理**：在原有签名载荷、卷所有权、全用户 Staged、无预配、即时重查门禁之内，允许经过核验的系统别名；不会因文本盘符为 C 就错误保留已确认属于 USB 的候选。错误链接和查询异常保留，记录原路径与查询错误。
6. **卸载终态**：拥有卷清理记录时，即使 AppX 卷已注销，也要核验精确系统包目录不存在，才能删除该卷清理记录。普通目录／链接仍在、读取被拒或返回内容不完整，均保留记录并报告 pending/failed。载荷身份无法校验时，不能跳过这个后置核验，保留记录并提示恢复完整介质后重试。没有所有权证据的既有系统状态继续列明保留，不能冒充已删除。

没有修改 USB 安全绑定、API Key、CCSwitch、签名校验、系统安全配置或真实 WindowsApps。没有手动删除 recovery.json 以解除保护。对确实无法通过 AppX 正常移除的系统孤儿链接，本版保证准确报告和保留证据，不声称已经自动修复 Windows 本身。

## 目标机验收要点

复制本次完成后的整个新目录，运行 CodexDesktopSetup.exe；不要混用旧 EXE。

- 正常 USB 安装：验证原生 Stage 完成、目标 PackageVolume 中有精确健康包，Register 后应用可运行且数据位于本机系统卷。
- InstallLocation 为 C 盘别名：应显示实际程序卷为绑定 USB，不再进入错卷迁移／回滚。
- 悬空／异常链接：日志应包含真实状态及 Stage HRESULT/ActivityId，不强删、不显示成功。请提供完整日志而非只截“权限不足”标题。
- 卸载：Windows 包状态、卷清理结果及精确系统包目录后置核验均通过才显示相应清理成功；pending 记录保留供重试。未选中的个人数据仍保留。

尚缺目标机该 Junction 的完整 LinkType/Target 和同一次 Stage 原始错误证据，不能把本轮隔离测试写成 Windows 10 家庭版真机验收通过。
