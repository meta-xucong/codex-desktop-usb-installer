## 已确认问题

1. `appx_volume_cleanup_script` 仅报告卷内包数量，未输出 FullName、FamilyName、InstalledLocation 与 PackageUserInformation。附件只能证明卷非空，不能证明该包是 Codex、来自哪次安装或没有其他用户。
2. 高级 `purge_user_data=true` 会在 Codex 主卸载阶段把 `%LOCALAPPDATA%\CodexAppxDataBackups\OpenAI.Codex_2p2nqsd0c76g0` 当普通用户数据立即删除；随后卷清理失败时，组合层仍使用“已保留诊断与恢复记录”的统一文案。该顺序会先销毁恢复 journal/备份再报告保留，附件中的矛盾成立。
3. `%TEMP%\CodexDesktopInstaller` 已在延迟最终清理白名单中；但只要卷或策略仍 pending，最终助手不会启动，因此约 802 MB 的本地暂存副本也不会清理。安装载荷不是卷恢复所需证据，用户明确卸载后可独立清除。
4. `Windows uninstall phase=completed scope=usb_bundle` 是 Codex 主卸载子结果，之后组合卸载仍可能因卷、策略或助手失败变成 `partialFailure`。行为本身分层，但 scope 名称会被误解为整个 USB 联合卸载已经完成，应改成明确的 `usb_bundle_codex_primary`；最终完成仍只能由组合结果/收尾报告给出。
5. 卷 journal 的随机文件名是写前 WAL 标识，不是 Windows Volume GUID；JSON 内 `volumeId` 才是物理标识。随机名本身不导致卸载失败，本轮不做破坏兼容性的重命名。

## 实现结果

1. `offline_payload::cleanup_package_claim` 只在存在卷 journal 且 Codex 主卸载已确认成功时运行。它校验当前 USB 包的 manifest 边界、文件大小、OpenAI Marketplace Authenticode 签名、主包身份、版本和架构，再生成唯一允许处理的 PackageFullName。可写的 JSON 或 AppxManifest 本身不再具有机器包删除授权。
2. `appx_volume_cleanup_script_with_claim` 使用管理员上下文查询目标卷的所有用户及全部包类型，并在诊断中有界列出 FullName、FamilyName、安装路径、架构和用户 InstallState。查询失败、字段缺失或卷身份不一致均停止，不当成空卷。
3. 自动包清理只接受：`state=owned`；原物理卷仍为同一 USB；PackageStore 为该卷精确 `WindowsApps`；FullName 等于签名载荷；PFN 为官方 Codex；主 x64 包；路径为 `WindowsApps\<FullName>`；不存在非 `Staged` 用户状态；不存在在线 provisioned 记录。移除前会重新查询，条件变化即停止；移除后再次查询，仍存在即报失败。其他包存在时只保留共享卷并列明包身份。
4. 精确 staged-only 候选使用 `Remove-AppxPackage -Package <FullName> -AllUsers`，不传 `PreserveApplicationData`。只有包已消失、卷中全部包为空且 `Remove-AppxVolume` 后卷注册也消失，才删除卷 journal。代码不递归删除 `WindowsApps`、不接管 ACL、不删除其他软件或其他用户仍使用的包。
5. `CodexAppxDataBackups\OpenAI.Codex_2p2nqsd0c76g0` 已从主卸载的立即用户数据清单移除。它只在系统卷/策略清理达到终态后，才由既有两阶段 finalizer 按用户明确选择的 Codex 高级清除项删除；partialFailure 时恢复证据仍在。
6. `%TEMP%\CodexDesktopInstaller` 与 `%TEMP%\codex-app-manager` 增加独立的立即清理。该步骤不依赖 AppX 卷能否注销，也不依赖桌面/文档目录能否写报告，因此卷 pending 不再遗留约 802 MB 的本地 MSIX；失败会进入组合结果，不能伪报全清。
7. USB 卷包移除/注销使用独立的 10 分钟有界管理员操作预算，避免在慢 U 盘或 Defender 扫描时沿用 120 秒小操作上限并中途强杀部署进程。普通策略操作仍保持 120 秒。
8. Codex 子阶段日志 scope 改为 `usb_bundle_codex_primary`。组合错误改为“Codex 主卸载已完成/未完成”，不会把 CCSwitch 或卷清理失败误写成整个联合卸载已完成；只承诺仍存在的诊断/恢复记录得到保留。
9. 附件建议的卷 journal 文件名重命名未采用：随机 UUID 是 WAL 操作标识，真实物理卷始终来自 JSON 内的 `volumeId` 并逐次交叉核验。改名不能修复故障，反而会破坏旧 journal 发现与兼容。

## 真实机验收与剩余边界

1. 真实验收必须从 v0.5.13 的 `CodexDesktopSetup.exe` 启动并接受一次 UAC；不能混用旧目录中的 v0.5.11 Manager。先点击联合卸载，最终以用户可见的 `Codex-Uninstall-Report-<批次>.json` 中 `status=completed` 且 `helperFinalization=removed` 为完全成功。
2. 预期的 v0.5.11 现场状态是：当前用户包已不存在，但 owned D: AppX 卷里恰有与当前 MSIX `OpenAI.Codex_26.825.5331.0_x64__2p2nqsd0c76g0` 精确一致的 staged-only 主包。该状态应被本版清理并注销空卷；随后可重新安装。
3. 若现场包是另一个版本、另一个 PFN、有 Installed/Paused 用户、有 provisioned 记录、路径不在原 USB，或查询/签名校验不可用，本版会继续 partialFailure 并列出实际包证据。这是防止误删的有意边界，不应通过模糊名称强制绕过。需要匹配该版本的原始签名介质或管理员人工确认后另行处理。
4. Authenticode 需要完整读取约 802 MB MSIX，慢 U 盘上可能明显耗时；签名预算为 5 分钟，卷清理预算为 10 分钟。超时、AppX 服务损坏、企业策略或杀毒软件阻止仍只能保留状态并报告，不能通过代码安全地保证成功。
5. 本轮修复解决的是报告所示的孤儿 staged 包、恢复证据顺序、暂存残留和状态语义；真实 Windows AppX 的最终结果必须由目标机复测证明，本文不把隔离模拟写成现场成功。
