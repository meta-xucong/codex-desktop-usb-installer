## 初始诊断（事实与推断分开）

1. 代码已确认：`Get-CodexRecoveryStagedPackage` 使用全机 `PackageManager.FindPackages()`，只有 FullName 筛选，没有卷筛选。staging 分支只在返回 null 时调用 Stage，因此其他卷同版本候选可使本轮 Stage 被跳过，再被 USB 路径断言拒绝。
2. 报告提供的原始错误是“身份通过但路径不符”，不是“包缺失”。由此推断当时返回了其他路径候选；实际路径尚无现场原文，不能认定一定是 C:，更不能认定是缺少某个策略值。
3. 当前 fresh/staging 日志本来支持在 staged=null 时重新 Stage；日志存在本身不是死锁根因。`lastDeployment=null` 也不能证明 Stage 没执行：旧代码仅将结果写入内存，在后置路径断言成功前未再次持久化。
4. 现有恢复测试把 Stage 与 GetStaged 整体替换了，主要覆盖 Stage 已落地后的中断，遗漏“尚未落地失败→同日志重试”和真实卷查询包装。需补充更低层测试。
5. 报告的 `AllowDeploymentInExternalVolumes` 必须写 1 暂无官方依据。微软文档的 `RestrictAppToSystemVolume` 本身管理其他卷（含 USB/SD），缺失/禁用时不限制；`RestrictAppDataToSystemVolume` 是独立数据策略，不是误用同一键名。正式引用与调查结论待补。

## 策略调查结论

- [微软 ApplicationManagement CSP](https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-applicationmanagement#restrictapptosystemvolume) 区分程序卷限制和数据卷限制：前者未配置／0 不限制非系统卷；后者 1 要求数据留系统卷。文档支持 SKU 表未列 Home，因此不把写入成功等同于 Home 一定执行；仍靠原生部署与实际位置核验。
- 本地 `C:\Windows\PolicyDefinitions\AppxPackageManager.admx` 第 55、65 行与 `zh-CN\AppxPackageManager.adml` 第 48、56 行交叉印证两项独立定义。本机 build 26200 不是目标机 19045，不能替代现场行为证据。
- 官方检索和本地 ADMX 没有查到 `AllowDeploymentInExternalVolumes`，因此没有依据将它写入或声称“设为 1 保证成功”。这不是证明任何内部实现中绝不存在该字符串，而是拒绝把未证实建议当系统契约。
- [微软 MSIX 版本专属部署说明](https://learn.microsoft.com/en-us/windows/msix/desktop/managing-your-msix-deployment-configmgr#enable-sideloading-on-target-devices) 指出 Windows 10 2004 以后默认启用旁加载；不能由缺少开发者模式值推断 19045 必然拒绝可信 MSIX。组织显式限制、证书或其他部署条件仍可拒绝。
- 当前 capability 已读取 Policies 下 AllowAllTrustedApps 与正确的 `SOFTWARE\Microsoft\Windows\CurrentVersion\AppModelUnlock` 路径，后者不是 Policies/Appx 的子值。未配置为 Unknown 不等于 Deny；保留这一行为。msix_policy_tx 实际管理 Codex 自动更新意图，不应塞入无依据的通用 HKLM 开关。
- 本轮没有改写 AppX 策略模块、旁加载能力或开发者模式。安装数据策略原有事务、回滚与卸载恢复逻辑保持不变。

## 最终实现

冻结恢复模块 SHA256：`786CF8E81E0A4EAF2C6F1956749EFC69CAC87CB7F2EDD88574C46EB840345387`；冻结夹具 SHA256：`62093BC6201E1CF0CE038E7CC9469BF0B7298F2D78A9D5A7D2C9C6758AE3EB8D`。本轮未修改的 `sys.rs` SHA256：`BA81421C5BDFA19686C0E8958B7F295193C35448B6958BD0E0796105F8C5D552`。

1. `Get-CodexRecoveryStagedPackage` 不再使用全机 `PackageManager.FindPackages()` 结果决定是否跳过 Stage。它先对已经绑定的目标 `PackageVolume` 调用按 PFN 限定的查询，再要求精确 FullName、唯一候选、健康状态以及 `<USB>\WindowsApps\<FullName>` 精确路径。目标卷查询错误会原样失败，不会被解释成“没有包”。全机同名候选只进入诊断字段，不能授权 Register、Remove、Move 或跳过 Stage。
2. Stage/Register 统一使用持久化的 write-ahead 记录。调用前写入 `started/nativeInvoked=false`；原生调用失败写入 `failed`、HRESULT、ActivityId/错误文本；原生调用完成先写入 `completed`，随后才重新查询和断言实际落点。因此即使 Windows 返回完成而包不在 U 盘，磁盘上的 `lastDeployment` 也不再错误地保持 null。
3. 旧 `mode=fresh, phase=staging` 日志不会被删除。只要 SID、物理 USB、载荷身份与哈希、根目录锁和日志绑定继续通过，目标卷仍无精确包时就沿同一日志安全重试 Stage；已经在目标 U 盘正确暂存的包会复用。失败路径不 Register、不 Remove，不覆盖用户数据。
4. WinRT await 层保留嵌套异常、COM HRESULT、异步状态与 DeploymentResult 错误；null 结果、取消、fault、结果级错误都显式失败。最终错误附带 phase、是否已调用 Stage/Register、目标卷查询结果、全机诊断候选、预期与实际路径、lastDeployment。
5. 没有加入 `AllowDeploymentInExternalVolumes`、开发者模式、C 盘回退或自动移动全机 staged 包。对后者的独立评估认为：公开 API 没有提供“仅在仍无用户注册时移动”的原子条件，查询与 Move 之间存在并发所有权变化窗口；本轮选择保留精确诊断并停止，避免移动其他用户或其他安装器的机器级载荷。
