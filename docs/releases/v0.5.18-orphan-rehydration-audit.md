# v0.5.18 悬空 staged 孤儿包重水合修复审计

日期：2026-09-06。输入现场：Windows 10 目标机存在精确机器级 `OpenAI.Codex_26.825.5331.0_x64__2p2nqsd0c76g0` Staged 记录，无当前用户注册、无预配记录、`InstallLocation` 为空且包文件已丢失。v0.5.17 先后调用 `Remove-AppxPackage -AllUsers` 和 `PackageManager.RemovePackageAsync(RemoveForAllUsers)`，分别收到 `0x80073CFA` 与 `0x80070002`，因此安装在正式 Stage 前停止。

## 根因

这不是新载荷、签名、U 盘卷识别或权限错误，而是早期失败版本遗留的 AppX 部署状态不一致：Windows 部署存储仍认识一个 Staged FullName，但对应包文件已被删除。删除接口需要读取缺失的部署文件来完成一致性事务，因而仅重复删除无法自愈。

现场还暴露两个次级缺陷：

- `PackageUserInformation.UserSecurityId` 在部分 Windows PowerShell/Appx 版本上是带 `Sid` 或 `Value` 属性的对象，直接转字符串会得到类型名，影响所有权诊断。
- 机器修复失败后旧 journal 仍停在 `state=running`，下次启动无法区分进程中断和已返回的确定失败。

## 修复设计

### 1. 精确识别，不扩大清理授权

- 同时查询当前用户、`-AllUsers`、预配包、Owner 状态、包路径以及每个在线 AppX 卷上的精确 FullName。
- 只有官方 PFN、x64 精确 FullName、无 Installed Owner、无预配记录的唯一对象可进入修复。
- 空路径／不存在路径继续标记为 `orphan-candidate`；一个公开 AppX 卷能够证明的健康 Staged 路径标记为 `staged-candidate`。多个包、多个卷、不同版本、未知 Owner 或查询失败均停止。
- SID 读取兼容字符串、`Sid` 和 `Value` 三种 PowerShell 投影；最终值必须满足 SID 语法。

### 2. 从可信 MSIX 恢复缺失文件

- 安装路径沿用恢复 journal 中已经计算的载荷 SHA-256；联合卸载重新从当前 U 盘发现完整 bundle，把 MSIX 复制到本地暂存目录，复核清单哈希、包身份、版本、架构和 OpenAI Authenticode。
- 进入系统修复前再次读取本地 MSIX 并核对同一 SHA-256；文件句柄从核验前一直保持禁止写入／删除，直到部署和落盘后置条件验证结束，消除“验完后被替换”的间隙。
- 优先通过 `Get-AppxPackage -AllUsers -Volume` 证明损坏记录所在卷；极端损坏导致卷投影消失时，只允许回退到 recovery context 已验证的唯一系统 AppX 卷。
- 调用公开的 `PackageManager.StagePackageAsync(uri, dependencies, ForceUpdateFromAnyVersion, recordVolume)` 恢复同一已授权 FullName 的包文件。完成后必须在选定卷中只找到一个健康同名包，且真实路径严格位于该卷的 `WindowsApps/<FullName>`。

微软文档说明 [`StagePackageAsync`](https://learn.microsoft.com/en-us/uwp/api/windows.management.deployment.packagemanager.stagepackageasync) 会在不注册用户的情况下 Stage 包，四参数重载可显式指定 `PackageVolume`；`ForceUpdateFromAnyVersion` 明确允许指定版本被 Stage/注册，不受现有更高版本影响。

### 3. 安装和卸载分别闭环

- **安装**：恢复文件后先调用 [`MovePackageToVolumeAsync`](https://learn.microsoft.com/en-us/uwp/api/windows.management.deployment.packagemanager.movepackagetovolumeasync) 把精确包迁移到当前已绑定 USB。迁移成功则直接进入既有注册／数据恢复流程；旧版 Windows 不接受 staged-only move 时，先用两条正式删除 API 清掉已恢复的记录，再执行正常 USB Stage。任何步骤出现新 Owner、版本变化或卷不唯一都停止。
- **联合卸载**：先尝试两条正式删除 API；如果仍是同一孤儿，才重水合并重试删除。必要时先迁移到当前 USB 再做最后一次精确删除。最终必须同时满足 AppX 投影为 none、精确 Windows 管理入口消失；否则保留现场并报告失败。
- 不删除私有 AppX 注册表，不修改 `PackageRepository/AppxAllUserStore`，不执行 `takeown`、`icacls` 或手工删除受保护 WindowsApps 入口。

### 4. 可恢复 journal

- `machineRepair.state` 支持 `pending / running / failed / completed`。
- 每次尝试先原子递增 `attempts`，上限 8；步骤写入 `step`，失败原文截断到 4096 字符写入 `lastError`，再向上抛错。
- 修复了 Hashtable 与 `PSCustomObject` 属性写入差异，避免看似更新但 JSON 仍保留旧值。
- 在“已重水合”“已迁移”“已删除”任一边界断电，下一次会重新观察 Windows 状态后继续，不盲目重复破坏性操作。

- Tauri manager：卸载清理授权必须携带本地已验签路径、精确 FullName 和 SHA-256；签名、哈希、身份任一不匹配均不授权。
- Windows x64 MSVC `custom-protocol` 编译检查通过；前端、发布工作流、离线 bundle、PE 清单、CRT 导入和最终目录哈希闭包均纳入发布验证。

## 无法规避的系统边界

- UAC 被拒、WDAC/AppLocker 禁止、AppX Deployment Service 本身损坏、另一个用户或预配包仍有效时，产品不会通过私有数据库手术绕过 Windows。
- 若 `StagePackageAsync` 连同已验签的同版原始 MSIX 仍无法让 Windows 修复自己的记录，错误会携带 ActivityId/HRESULT 和 journal 步骤保留；此时应修复 Windows 部署组件，而不是夺取 TrustedInstaller 目录权限。
- 重水合需要系统卷或记录卷具备“MSIX 展开大小 + 512 MiB”临时空间；不足会在部署前明确停止，不留下新的半成品。
