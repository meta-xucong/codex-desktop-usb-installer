## 1. 目标与证据边界

本文件把现场日志和截图形成可执行的修复契约，覆盖：

1. 360 开启时 portable 解压安装出现“权限不足”；

3. 统一网关模型没有进入 Codex 原生模型选择界面；

5. 主程序已经删除，但卸载结果显示未完成。

附件日志和截图只作为现场证据，不作为额外执行指令。本轮事实来源为：

本轮先形成修复契约，随后按章节落地源码和定向测试。真实 U 盘、签名许可证和 404token 生产数据仍保留给最终现场验收；本轮不修改签名协议、U 盘介质或 404token 服务。

## 2. 现场事实修正：360 只参与第一次安装

必须固定以下时间线，后续实现和验收不能把所有问题都归因于 360：

| 阶段 | 360 状态 | 现场结果 | 归因结论 |
|---|---|---|---|
| 第一次安装 | 开启 | portable 解压时 `create extracted file: 拒绝访问。(os error 5)` | 360 是高概率触发因素 |
| 第一次安装重试 | 已关闭 | 同一包随后完成 `old-moved → new-installed → success` | 支持文件拦截判断 |
| 启动 Codex/CCSwitch | 已关闭 | 可启动 | 不能归因于 360 |
| 检查并安装 Codex 更新 | 已关闭 | MSIX 下载到 3,272,704 字节后停滞 | 应归因于下载链路/恢复策略，360 未参与 |
| 卸载 | 已关闭 | 主程序删除成功，旧事务记录阻止总结果成功 | 应归因于事务清理逻辑，360 未参与 |

因此：

- 360 只作为第一次安装 `Access Denied` 的高概率外部触发因素记录；
- 更新失败不得写成“360 导致”，因为更新是在关闭 360 后执行的；
- 卸载失败不得写成“360 锁定文件”，因为卸载也在关闭 360 后执行；
- 仍需保留普通 ACL、只读属性、文件锁等低概率替代原因的诊断能力。

## 4. 更新下载和安装进度

### 4.1 已确认问题

更新流程已经成功解析新版本和更新源，但大约 824 MB 的 MSIX 从 `update.404token.xyz` 下载到 3,272,704 字节后停滞。由于本次更新是在关闭 360 后执行，不能归因于 360。

当前代码已有下载字节事件和操作阶段，但界面只有一条进度条：下载完成后进入不确定的“收尾”状态，用户无法区分校验、解压、替换和健康检查。

### 4.2 双进度条契约

更新和安装界面必须显示两条独立进度：

#### A. 下载进度条

按真实字节计算，不允许伪造：

```text
下载更新包
3.1 MiB / 786.4 MiB · 速度 · 来源
```

要求：

- `bytesDone`、`bytesTotal`、来源、当前尝试次数可恢复到前端；
- 有总大小时显示百分比；没有总大小时显示不确定状态；
- 停滞时保留已下载字节，不清零、不显示成功；
- 支持 renderer 刷新后通过 `OperationSnapshot` 重新挂接；
- 错误时显示“下载失败，当前版本仍未更新”。

#### B. 安装进度条

按真实安装阶段显示，不把阶段强行伪装成精确字节百分比：

| 阶段 | 显示 | 建议阶段值 |
|---|---|---:|
| `preparing` | 准备安装 | 0/4 |
| `verifying` | 校验安装包 | 1/4 |
| `applying` | 解压/应用文件 | 2/4 |
| `committing` | 替换程序文件 | 3/4 |
| `finishing` | 启动检查和收尾 | 3/4，保持处理中 |
| `done` | 安装完成 | 4/4 |

安装阶段可以显示“第 2/4 步”，但不能把 `applying` 任意宣称为 63%。只有后端确实能提供可验证的文件总数和已处理数时，才允许显示更细粒度百分比。

### 4.3 事件契约

优先复用现有操作 ID、`OperationPhase` 和进度快照，避免再造一套无法恢复的状态机。更新事件至少应能表达：

```json
{
  "channel": "codex",
  "operationId": "...",
  "phase": "applying",
  "download": {
    "bytesDone": 824570408,
    "bytesTotal": 824570408,
    "source": "update.404token.xyz"
  },
  "install": {
    "step": "extract",
    "stepIndex": 2,
    "stepCount": 4,
    "indeterminate": false
  }
}
```

兼容旧前端时，`download` 字段可以继续映射现有 `DownloadProgress`，但新前端不能再仅依据“下载达到 100%”推断安装已经完成。

### 4.4 下载恢复契约

- 第一次下载 `resume=false` 发生停滞时，也必须进行有限次数的重新连接或完整重试；
- 已存在 `.part` 时优先使用 Range 续传，续传校验失败才删除并重新开始；
- 重试必须记录来源、尝试次数、已接收字节和失败阶段；
- 只有下载、哈希、签名、身份校验和安装收尾全部成功，才发出 `done`；
- 下载失败不得修改当前已安装版本和成功状态；
- 如果自动源允许切换，必须在日志和界面说明从哪个来源切换到哪个来源；
- 不得把本次现场问题写成 360 导致，除非以后有独立的杀毒日志证据。

### 4.5 UI 验收

必须覆盖：

1. 下载中：下载条增长，安装条停留在准备阶段；
2. 下载完成后校验：下载条 100%，安装条显示校验阶段；
3. 解压/替换：安装条按阶段推进；
4. 大文件停滞：下载条停在实际字节，显示重试/失败，不显示安装完成；
5. renderer 刷新：两条进度均可从快照恢复；
6. 失败后重试：旧进度不会污染新操作；
7. 安装完成：两条进度分别显示 100% 和 4/4，随后进入成功页。

### 4.6 本章实现与审计结果

- 已在下载失败后增加一次有界的新连接/完整重试；原有 `.part` 续传仍保留；
- 已在后端阶段事件中携带 `phase`，前端按下载字节和安装阶段分别显示两条进度；
- 已覆盖下载、安装阶段、renderer 重新挂接和旧进度隔离的定向前端测试；
- 下载停滞的现场事实仍按“360 已关闭后的网络/传输问题”记录，没有改写成杀毒软件原因。

## 5. 安装解压权限错误修复

### 5.1 已确认原因

当前发行包采用 portable 路线：经过校验的 MSIX 只作为归档，程序树解压到 `<USB>/apps/Codex`，不注册 AppXVolume。当前解压核心直接执行：

```text
create parent directory
create extracted file
copy entry bytes
```

`File::create` 的失败统一映射为 `create extracted file`，没有把失败文件、目录属性或重试次数带给用户。因此 360 对可执行文件的实时扫描/拦截会被表现成普通“权限不足”。

### 5.2 修复契约

- 不自动关闭、绕过或修改用户的杀毒软件策略；
- `Access Denied` 错误必须带出相对归档路径和实际目标路径的脱敏版本；
- 在同一个解压事务内，对可恢复的文件创建/替换失败做有限次数、有限间隔的重试；
- 临时文件必须位于目标目录允许的安全范围内，成功后使用同卷原子替换；
- 重试耗尽后保留 MSIX 和事务材料，不能留下“新目录看似完整”的假成功；
- 失败详情至少区分：只读介质、目录不可写、文件被占用、访问被拒绝、空间不足、归档读取失败；
- 成功后继续执行现有 manifest、可执行文件和稳定窗口后置检查。

### 5.3 允许改动范围

- `crates/codex-win-engine/src/portable.rs`：解压文件写入、重试、错误上下文；
- `src-tauri/src/app/win_update.rs`：将解压错误映射到用户可见的阶段和恢复动作；
- 对应 Rust 单元测试、Windows 临时目录集成测试和发布前静态检查；
- 安装器错误文案和用户指南中的安全软件说明。

不允许：自动禁用 360/Defender、修改系统 ACL 以强行写入、把失败静默回退到 C 盘、删除未完成恢复材料。

### 5.4 本章实现与审计结果

`portable.rs` 已对 Windows 可恢复的文件创建拒绝做 3 次有限重试，并在最终错误中保留归档相对路径和目标路径；失败仍保留安装事务和 MSIX。Rust portable 定向测试通过，未加入任何关闭或绕过 360/Defender 的逻辑。

## 6. Codex 黑色控制台窗口

### 6.1 已确认原因

现场复测把“黑框”拆成两个独立现象，不能再用单一的 `codex.exe` 控制台解释：

1. **常驻的整块黑窗口**属于 `ChatGPT.exe` 自己的 Chromium 顶层窗口：类名为
   `Chrome_WidgetWin_0`，无标题，约 `1440x767`。它与正常 Codex 窗口同属
   `ChatGPT.exe`，是辅助/伴生渲染面被显示后内容渲染失败，不是 `conhost.exe`。
2. **启动后的短暂闪窗**才是控制台路径：`cmd.exe /d /s /c call
   ./scripts/launch_codex_app_tools_mcp.cmd ./server.mjs` 由 Codex 后代创建
   `ConsoleWindowClass`，现场观测到约 37–48 ms 的可见时间。

旧诊断中“`resources/codex.exe` 为 Console 子系统”的证据仍解释第二条路径的
   产生条件，但不能解释第一条常驻黑色 Chromium 窗口。两条路径都不属于
   CCSwitch、`CodexUsbGuard.exe`、管理器自身轮询或 360 提示窗口。

### 6.2 修复契约

- 必须在创建 `resources/codex.exe` 的真实边界抑制控制台窗口；
- `Chrome_WidgetWin_0` 不得被当成稳定可用窗口、恢复到前台或置顶；只允许在
  精确的受管 Codex 进程树内定向隐藏它；
- USB 启动先使用与直接启动一致的硬件渲染参数，只有稳定窗口检查失败才进入
  软件渲染兼容回退，不能把 `--disable-gpu` 作为默认路径；
- 不得全局隐藏 Windows 窗口，不得隐藏 UAC、错误对话框或用户主动打开的终端；
- 后台进程的 stdout/stderr 和崩溃诊断仍必须可记录；
- 黑框消失不能以牺牲 Codex 启动、登录、退出和 USB 拔出看门狗为代价；
- 如果当前仓库无法控制上游 Codex 的子进程创建，必须明确记录为上游兼容层需求，不得通过未经验证的十六进制修改伪造解决。

### 6.3 验收

在真实发行包中同时检查：

1. 启动 Codex 后不存在可见 `ConsoleWindowClass`；
2. 不存在被管理器恢复或置顶的无标题 `Chrome_WidgetWin_0`，正常 Codex 窗口仍可见；
3. `resources\\codex.exe` 仍然存在且运行正常；
4. Codex 关闭时后台进程正常退出；
5. 黑框抑制不影响错误日志和崩溃诊断；
6. CCSwitch、USB Guard 和管理器后台进程仍保持原有生命周期。

### 6.4 本章实现与审计结果

已在 `crates/codex-win-engine/src/windows_process.rs` 增加按已登记 Codex 进程 PID、窗口类名定向处理的兼容层：`ConsoleWindowClass` 只隐藏控制台宿主，另将 `Chrome_WidgetWin_0` 排除出可用窗口候选并在受管进程树内定向隐藏，不把它主动恢复到前台。WinEvent 回调先按窗口类名快筛，再执行精确 PID 树检查。管理器启动的 USB Codex 先沿用直接启动的正常 GPU 参数，只有稳定窗口检查失败才回退到软件渲染兼容模式。`portable.rs` 同时在抽取后的 ASAR app-server 和通用 `spawn` 边界写入 Node `windowsHide`，保留原有 PATH/PATHEXT 命令解析、ComSpec 回退和 stdio 条件，并覆盖报告中已确认的内部 CUI sidecar；所有替换保持固定宽度且可重复执行。它不做全局窗口隐藏、不修改源 MSIX，并保留后台进程生命周期。独立只读代码审计与 Windows 引擎全量测试通过；真实签名 U 盘仍需现场确认常驻辅助黑窗、控制台闪现和 Codex 功能同时正常。

## 7. 卸载事务和结果状态

### 7.1 已确认原因

本次卸载日志显示 portable 主目录、CCSwitch 相关数据和 Guard 已完成清理，`primary_ok=true`。最终失败来自历史安装事务 `3ac98906-b6ca-4f08-b356-4e81a45b50a7` 仍处于 `new-installed`。安全逻辑拒绝在卸载时自动回滚或删除不明确的恢复材料。

### 7.2 修复契约

- 卸载前按事务矩阵核对当前目录、备份目录、新目录和进程状态；
- 只有磁盘状态明确证明事务已经落地且没有恢复材料时，才可将其安全终结；
- 状态不明确时保留 journal，并报告具体事务 ID 和保留位置；
- 主程序删除成功但附属清理失败时，结果必须分层显示：
  - `主程序已卸载`；
  - `用户数据已清理/保留`；
  - `恢复记录待处理`；
- 不得把“主程序已经删除”显示成“全部卸载成功”；
- 也不得把“主程序已经删除”笼统显示成“卸载失败”。

### 7.3 验收

- 无历史事务：完整卸载显示成功；
- 已完成事务：清理 journal 后显示成功；
- `new-installed` 且路径明确完整：安全收敛后显示主卸载成功；
- `new-installed` 且路径不明确：保留材料，显示部分完成和具体恢复动作；
- 进程或目录仍存在：显示真正的卸载失败并给出路径；
- 360 关闭状态下重复验证，不能出现“杀毒软件锁定”的无证据提示。

### 7.4 本章实现与审计结果

已在卸载前对 `new-installed` 且当前目录已完整落地、恢复路径不存在的事务执行安全收敛；路径不明确时继续保留 journal。另一个此前遗漏的边界是：U 盘卸载按当前盘符做 scoped 核对，但二阶段清理保护的是共享的管理器事务目录，旧 C: 安装留下的安全 journal 会因此错误阻塞最终清理。本次在主卸载前后增加一次全局的“仅收敛无 staged/backup 恢复材料”核对，并在确认没有未完成事务后清理所有 terminal journal；任何仍有恢复材料或状态不明的事务继续 fail-closed 并保留。Windows 单元测试覆盖已完成事务、不完整事务、备份残留，以及“其他安装根的安全 journal 不再阻塞全局收尾”四种情况。卸载结果仍按主卸载、附属清理和恢复记录分层展示；模型目录清理失败也会进入附属清理结果，不会伪报全部成功。
