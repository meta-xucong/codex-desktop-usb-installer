# U 盘版 Codex 测试机验收、回退与交付手册（2026-10-25）

**状态：待测试机执行。** 代码实施与本地自动化已有单独授权；本手册不授权真实安装/替换、用户配置、凭证或数据操作。先读[主开发规范](CODEX-USB-BASIC-CAPABILITIES-REPAIR-PLAN-20261025.md)，按[回归矩阵](CODEX-USB-BASIC-CAPABILITIES-REGRESSION-MATRIX-20261025.md)只执行与本轮已变更模块相关的步骤，向[证据台账](CODEX-USB-BASIC-CAPABILITIES-EVIDENCE-LEDGER-20261025.md)登记结果。

## A. 进入测试机前检查

满足下列条件才开始候选包测试：

- [ ] 当前源码候选身份明确；工作树既有脏改动已保全，不与其他执行者并行改写同一文件。
- [ ] 候选版本、架构、package manifest、file manifest/checksum 与实际 USB 文件哈希可相互核对。
- [ ] 官方参考包为相同版本/架构/发布者，签名验证结果和哈希已记录；不能用不同版本参考推断目标文件应为 CUI 或 GUI。
- [ ] 使用独立测试机账户/可恢复 profile，USB `CODEX_HOME` 不与标准 Codex 数据/凭证合并；已确定日志脱敏位置及保留期限。
- [ ] 没有自动/人工后台升级或旧 manager 并发写入目标 payload；不覆盖正式测试机现有用户数据。
- [ ] 测试任务按矩阵分为只读、无副作用、可能外发、可能计费、可能删除。后三类先停止，取得相应单独授权或改用可逆 fixture。

任一必需项不满足：记 `ENV_BLOCKED` 或 `NOT_RUN`，写清阻断原因，不通过复制到隐藏位置或清空 profile 绕开。

## B. 建立无计费基线

**本轮代码状态更新：**当前工作区 `src-tauri/src/app/codex_theme.rs::launch_codex_with_cdp` 已通过共享 helper 接入 USB model-catalog preflight；preflight 或启动失败时不会运行 marker completion，只有启动成功才完成。该子项不需要重复开发，但需先以第0章方式确认待测源码身份，再在 R-03 中完成四条启动路径验证。现有 5/5、7/7 和 802/0/6 日志见证据台账 E-11；其余早期全量尝试有失败，日志未绑定源码指纹，不能作为当前完整候选结论。USB 实机尚未执行。

按该顺序做，先不要改变程序、配置或模型字段：

1. 记录 USB 安装介质身份、候选目录、实际 CODEX_HOME、Codex/CCSwitch 版本、provider/model 和新会话 ID；秘密只记录存在与否，不读取/复制值。
2. 通过 UI 正常打开一次，记录启动进程、父子 PID、cwd、环境摘要、窗口可见性及 Codex 启动日志。普通、主题、事务重启入口分别单独记录，不将一次启动外推到其他入口。
3. 对当回合保存工具清单和来源，分别标注文件/命令 host、Browser、Node、Search/tool_search、DIRECT/DEFERRED MCP、App Tools、native multi-agent。
4. MCP 分阶段记录进程启动、initialize/ready、`tools/list`、`media_prepare` schema/响应；在任何生成前停止，先确认这几层是否正常。
5. 对跨会话只使用明确授权的隔离测试会话和无副作用消息，验证目标 ID、目标端收件和返回回执。`thread/list`、请求已发送字段或工具配置本身都不是收件证明。
6. 使用相同 profile、相同模型/请求建立一次单变量比较。每轮只变更一个因素并记录恢复方式，不同时切换提示词、MCP launcher、PE 子系统和 focus 策略。

## C. 原包、二进制和启动回退

1. 对原包验证版本、发布者、签名链和包哈希；从原包提取的目标文件要单独记录路径、文件 hash 和 PE subsystem。包的签名不自动证明当前 USB 文件未被改写。
2. 本轮只验收从当前源码重新构建的新候选；不恢复、迁移或测试旧 USB payload。PE 检查只判断新候选是否遵守源码规则；不得按名字或 subsystem 推断旧文件来源。
3. App Tools `.cmd` 与直接 bundled Node 分别记录实际命令、Node 路径、cwd、argv、环境变量、timeout、stderr、退出码、initialize、工具表和跨新会话结果。恢复官方 `.cmd` 前要有证据说明直接启动导致了具体失败，且测过 cmd 窗口副作用。
4. 窗口问题记录真实产生窗口的进程与父级、用户动作、前台窗口变化及插件对账日志。`reason=focus` 本身不能证明窗口激活导致插件失败。

若新候选身份或必要对照样本不满足前置条件，相关行保持 `NOT_RUN`；不要触碰旧 USB 介质。

## D. 分模块执行和停止点

| 阶段 | 继续条件 | 停止条件 |
|---|---|---|
| 启动/环境 | 版本身份和 USB profile 正确，子进程环境可采集 | 错误包、profile 混用、检测到非预期用户数据目标 |
| MCP 握手/工具表 | server ready，错误能归属到具体阶段 | server 未启动或工具清单不明；先定位，不测生成 |
| 模型/委派 | 模型与 provider 明确，工具在当前回合可见 | 请求目标或路由不明；不得重发未确认任务 |
| Browser/Search/Node | 对应工具真实注入，测试动作无副作用 | 只有静态配置或公开 issue；记录未验证，不绕宿主 gate |
| 媒体生成/计费 | 任务已获单独授权，额度和目标明确 | 未授权、历史任务状态未知、可能重复计费 |
| 卸载/清理 | 专用可恢复测试机，目标清单已审核并单独授权 | 真实用户 profile、范围不清或 USB 介质会被纳入删除 |

## E. 故障回退和事故留证

- 一次只回退当前变更章；使用该章保存的源码 diff、配置备份或同版文件备份。不得 reset/clean 整个工作区或重装覆盖来“恢复”。
- 对配置回退保留原始字节、编码/BOM、权限和路径；对 PE/包文件保留原始 hash、签名结果和 manifest 关联。
- 出现跨 profile 写入、凭证外发、错误会话投递、意外付费、非预期删除或文件 hash 不匹配时立即停止后续步骤，保留最少必要脱敏证据并报告；不要自动重试、清理或修复现场。
- 若真实配置/二进制或用户数据已改变，先记录准确目标、执行动作、结果状态（成功/拒绝/挂起/不确定），再按授权的恢复流程处理。未知结果先检查，不重复发送有副作用动作。

## F. 最终交付门槛

交付包/源码只有在以下证据齐全后才可称为本候选验收：

1. 只要求本轮实际修改项及其相邻回归行达到 `PASS`；条件模块只有在发现直接本仓缺陷并纳入实施后才变为必测。未执行行继续标 `NOT_RUN`/`ENV_BLOCKED`，不得据此扩大修复面，也不得宣称完整能力验收。
2. Rust 定向、相邻和全量测试以及前端测试记录本轮实际命令、结果、忽略/失败归因、运行环境、源码/测试二进制指纹。旧日志的数值不继承到新源码。
3. check/lint/format/build 与 release workflow 结果绑定同一候选；最终包 manifest/checksum 与实际产物哈希一致。只有源码测试时不称打包验收；只有桌面开发机结果时不称 USB 测试机 E2E。
4. 测试机使用新会话完成各目标工具的真实工具清单和调用证据；MCP prepare 与生成、App Tools 跨会话与 native multi-agent 分别汇报。
5. 所有 `ENV_BLOCKED`、授权未完成、未知任务状态和可接受风险保持可见；不以删除测试、跳过失败或改变目标 profile 来凑绿。

## G. 必须单独授权的动作

本手册没有授予真实卸载、删除用户数据、替换已安装程序/PE、读取或使用用户凭证、向外部账户发送消息或执行可能计费的图片/媒体生成权限。当前产品卸载约定仍是两步确认后清理本机 Codex/CCSwitch/受管能力数据并保留 USB 安装介质；仅在专用可恢复测试环境、另行授权后验证真实清理。
